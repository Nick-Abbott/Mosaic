1. EXECUTIVE RECOMMENDATION

Keep one repository, two release versions, and one public org.buildmosaic.analysis
plugin. Publish the four Runtime modules together. Publish the Analysis plugin and
all selected extractor binaries together under the Analysis version; keep the
compiler-independent implementation internal and bundled as today.

The first implementation priority is a fail-closed Runtime semantic handshake,
BEFORE expanding the compiler allowlist. Give Runtime JARs a stable, small
compatibility descriptor. An analyzer accepts it only if it understands every
required, immutable semantic capability. Initially use ONE coarse capability,
"mosaic.canvas-analysis/1", covering the existing public API analysis matrix and
its deliberate unknown boundaries. Do not create a capability for each API method.
Keep the summary format and summary interpretation epoch separate. Use additional
capabilities only when evidence establishes independently useful variation.

This is candidate D, a small hybrid of B and C. A versioned capability is a semantic
contract, not a minimum Analysis release. A later Runtime with unchanged semantics
can require the same capability indefinitely. A later Runtime introducing a new
analysis obligation declares it in the OLD descriptor grammar; an old analyzer
must reject the unknown token. Release numbers are identity and diagnostics, never
the semantic comparison algorithm.

Use one checked-in machine-readable registry with explicit complete combinations,
artifact identities, reusable evidence references, and Kotlin family release dates.
Generate the selector, runtime requirements, website lookup/static view, and README
summary from it. Certification is not a transitive closure of pairwise tables.
Every advertised complete tuple gets a small real external-consumer end-to-end
check, with larger suites reused only within explicit, content-identified scopes.

At the assessment date, eleven stable compiler/KGP matching pairs are in scope:
2.2.0, 2.2.10, 2.2.20, 2.2.21, 2.3.0, 2.3.10, 2.3.20, 2.3.21,
2.4.0, 2.4.10, 2.4.20. Kotlin 2.2 expires on 2026-12-23; it cannot be omitted
from an October 1.0 certification plan. The release date of Mosaic 1.0 is not yet
known; re-evaluate this list on that actual date. No 1.0 artifact has been certified
by this investigation. Prior research substantially reduces technical uncertainty
for four versions, but does not fill the final release-certification rows.

Two limits must remain explicit:
* Existing 0.x analyzer binaries do not implement the handshake. A descriptor
  cannot make arbitrary already-shipped code read it. Establish the protocol before
  the first Analysis release certified for Runtime 1.0; do not grandfather old
  plugins based on their number or a successful compile.
* The published Runtime itself must be consumable on Kotlin 2.2. The current build
  emits language/API 2.4 output and uses current dependencies. Passing extraction
  tests on 2.3 does not prove 2.2 Runtime consumption. Resolve that before 1.0.

Relevant baseline implementation (all paths relative to cf49095):
* mosaic-core and mosaic-test own public runtime APIs. mosaic-test compiles with
  friend access to core's internal engine. mosaic-opentelemetry exposes installation
  plus the observation integration; its POM supplies API, not an application SDK.
* buildSrc/src/main/kotlin/kotlin.convention.gradle.kts uses JDK 21 to build,
  JVM 17 bytecode, languageVersion/API version 2.4, and stable moduleName.
* gradle.properties has mosaic.version=0.7.0. There is no root version.properties.
  The Gradle plugin generates org/buildmosaic/gradle/version.properties from
  project.version; the installed plugin reads that resource.
* base.convention applies the single version to all projects. release and
  releaseToMavenCentral publish both trains; release.yml expects a numeric tag
  matching mosaic.version and then publishes Central plus the Plugin Portal.
* The BOM already constrains only core, test, and opentelemetry. Keep this scope.
* analysis-core has no publication. Compiler and Gradle JARs each bundle it and
  its dependencies. Compiler API/KGP dependencies are compileOnly. Preserve that
  ownership; independently published analysis-core would add an unnecessary
  consumer alignment problem.
* SourceContractExtractor.operation/isIntrinsic recognize fully qualified runtime
  names, parameter names, types and selected factory/delegate patterns. For example
  compose overloads share a recognized owner/name. There are meaningful Unknown
  branches, but no runtime-release or runtime-semantics validation. An added
  overload could match an old intrinsic path; unknown fallback alone is inadequate.
* SummaryCodec: resource META-INF/mosaic-analysis/v1/summary.json, format 5,
  semantics analysis-contract-3, toolVersion prototype-11, compiler 2.4.20.
  The writer hardcodes all these. The reader checks format, semantics, exact
  compiler, completeness, main source set, module identity, hash, model and
  duplicate locators. No independently negotiated capability set exists today.
* SourceShardCodec uses shardVersion 2 without compiler/extractor identity.
  extractMosaicMain assembles current-source shards and an explicit empty summary.
* MosaicSummaryTransform copies only the selected summary resource. No resource
  means no output, preserving missing-metadata unknowns. MosaicDependencyReader
  decodes all selected summaries and reports errors using transformed filenames;
  it discards producer metadata after decoding to ModuleContract.
* MosaicAnalysisPlugin selects one fixed compiler artifact. Its
  productionCompilerVersion is the KGP package version, not necessarily the
  effective compiler. ExtractMosaicTask validates exact KGP and artifact manifest
  versions, and recognizes Kotlin default artifacts by 2.4.20 filenames.
* VerifyMosaicTask validates local metadata, then LIBRARY returns a library report
  BEFORE reading dependencies. APPLICATION checks dependency summaries/owners and
  evaluates. MosaicGraphTask has a separate reader path. JAR assembly depends on
  extract, not verify. Every one of these paths needs the common handshake.
* Existing compiler PUBLIC_API_MATRIX.md and Gradle INVALIDATION_MATRIX.md are
  durable semantic/invalidation specifications; extend these, not parallel suites
  that repeat the same evaluator behavior at a more expensive layer.

3. RUNTIME → ANALYSIS NEGOTIATION

3.1 Candidate comparison

A. Runtime minimumAnalysisVersion
  Simple to display, but release ordering is a poor semantic predicate: capability
  backports, compiler support retirement, and independent trains make >= neither
  necessary nor sufficient. Old dependency summaries also need interpretation
  rules. A minimum version may be a diagnostic hint, never the admission test.

B. Runtime required capability set
  The old parser can reject a token it has never seen. A set inclusion check does
  not require Runtime/Analysis equality or knowledge of future runtime numbers.
  The cost is disciplined authoring and coverage of the declared requirements.
  A per-symbol capability inventory would be premature complexity.

C. Independently versioned semantic epoch
  One opaque contract identifier is simple and reliable; use exact membership in
  the reader's supported set, never numeric >=. A single epoch conflating runtime
  semantics, wire shape, compiler ABI and tool release causes needless rejection.

D. RECOMMENDED: stable required-capability envelope + existing summary epoch
  One coarse versioned runtime capability initially; a format/meaning epoch for
  summary payloads; no release minimum. This retains a small protocol while giving
  unknown future obligations an explicit fail-closed representation. Do not add
  a separate runtime epoch field that repeats the sole capability's version.

3.2 Descriptor v1 (proposed public inter-tool protocol)

Every Runtime JAR includes exactly one resource at the fixed path
META-INF/mosaic/runtime-compatibility.json. The BOM is a platform POM and has no
JAR; its identity is established by the release manifest, not a fake resource.
Example, NOT an existing artifact:

  {
    "descriptorVersion": 1,
    "module": "org.buildmosaic:mosaic-core",
    "runtimeVersion": "1.1.0",
    "requires": ["mosaic.canvas-analysis/1"]
  }

For test and tracing the module field changes; their requirements declare only
analysis-relevant obligations. Do not require modeling tracing privacy or resource
closure merely because those are Runtime behavior guarantees: they remain outside
Canvas-availability analysis. Changes to callbacks that affect availability must
be reviewed against the existing unknown boundary and can require a new token.

Define the protocol grammar before shipping the reader:
* Exact UTF-8 JSON object, required fields with exact types, no duplicate object
  keys, no duplicate/blank requirement strings, bounded size, no multiple JAR
  entries for the path. Require a nonempty known baseline capability.
* Unknown fields in v1 are errors. Reserve no arbitrary critical extension field.
  New mandatory semantics MUST be an unknown token in requires, or a new
  descriptorVersion at the SAME path. Both fail closed in every v1 reader.
* Capability identifiers are opaque strings with immutable, documented internal
  meaning. Reader.supportedCapabilities is an explicit finite set. Unknown token
  => compatibility error even if the local program appears not to use the feature.
* runtimeVersion is exact release identity, not a comparison operand. Match
  descriptor module/version to resolved component identity where Maven identity
  is available, and to the embedded identity for project/local JARs. Reject
  duplicate/shadowed Runtime owners, missing core, or mixed selected Runtime module
  versions. Do not silently force alignment; recommend the runtime-only BOM.
* Scan selected artifacts, not ClassLoader.getResource(), which would return only
  one of several duplicate resources. Treat unidentifiable/repackaged Runtime
  ownership conservatively; no positive proof based on a package name alone.
* The path and fail-closed meaning remain stable for all protocol-aware readers.
  Do not move the path for v2: the old reader must see and reject v2, not mistake
  its absence for a legacy Runtime.

Runtime owns the required contract. Analysis owns supported contracts. A pure
compatibility decoder/checker in analysis-core is shared by the Gradle plugin,
extractors and metadata reader. Runtime depends on no Analysis code at runtime;
its release resource is generated from its registry release record. The registry
has named contract definitions with a specification hash and test references;
changing a definition in place is prohibited.

The initial capability freezes the meanings of lookups, Canvas registrations and
construction/layer ordering, scoped Mosaic provenance, Tile creation/delegation,
compose execution, stable key/export identity, default effects and conservative
omission boundaries described by the current public API matrix. It promises a
sound interpretation, not that every program becomes fully verified.

3.3 Enforcement and ownership

PROPOSED task/data flow:

  selected compile Runtime JARs -> descriptor extraction -> compatibility preflight
             |                                      | (before compileKotlin)
             v                                      v
       normal KGP main compilation + selected extractor -> source-relative shards
                                                        -> extractMosaicMain
  selected dependency summaries ------------------------> validated contract input
  selected runtimeClasspath Runtime descriptors --------> verification/packaging
                                                        -> verify / graph / jar

Use a raw-resource transform for Runtime descriptors and summaries, with explicit
absent markers and origin information. This extends/replaces MosaicSummaryTransform
without teaching it semantic policy. Resolve an artifact view lazily; store
serializable component coordinates, resource paths and digest associations for
exact diagnostic attribution. Read compiler classpaths as declared inputs; never
load dependency classes to inspect resources.

Compatibility preflight is mandatory for APPLICATION and LIBRARY and for a JAR
that will carry a summary. Runtime requirements gate intrinsic recognition before
compilation. The extractor verifies the same contract at its compiler entry point
(direct K2 fixtures/CLI paths cannot bypass it), and stamps the actual handshake
into every shard. Gradle can pass a generated manifest, but the extractor must
validate it against its actual selected compiler classpath, not trust an arbitrary
"validated=true" option. Reuse the pure decoder, do not duplicate its rules.

Keep dependencies' summary BODY changes off compileKotlin's extra input path.
They remain verification inputs as today. Runtime descriptor semantics changes
are a separate compile input and must invalidate extraction. RuntimeClassPath
checks must not introduce a compile/project-jar cycle: precompile checks use the
compile-selected Runtime; a packaging/verification gate compares runtime-selected
Runtime modules afterward. Resolve only Runtime identities/descriptors for that
comparison, not arbitrary execution effects. If compile and runtime select
different Runtime versions, fail with alignment guidance for the initial policy.
No certification is implied for running against a different deployment classpath.

Assembly validates local provenance and required capabilities even for NO_SOURCE.
Packaging and LIBRARY mode validate every present dependency envelope and their
requirements, even though they select no application roots. APPLICATION and graph
consume the same validated metadata result. Use one internal ValidatedContracts
value/checker; do not maintain separate accept/reject logic in graph, verify and
packaging. Its construction is the admission boundary; raw ModuleContracts are
not admissible dependency inputs to these production entry points.

STANDARD/STRICT and rule severities never downgrade compatibility errors. On an
error, replace/delete the prior report and do not emit a usable complete summary
or a success report. Old physical files must be rejected by provenance checks on
subsequent assembly. Task failure is authoritative; the report explicitly says
"Compatibility failure; no verification result produced."

3.4 Missing metadata, incompatible metadata, and capabilities are different

Ordinary library with no summary:
  Preserve UNVERIFIED at a reached unknown boundary; do not fabricate an empty
  effect-free contract. Unrelated missing summaries need not make every root
  unverified. STANDARD may pass with a warning; that is not FULLY VERIFIED.

Present incompatible/malformed summary:
  Always a compatibility failure, not an unknown or ignored file. Include selected
  component identity, producer Analysis/compiler, installed Analysis, actual and
  accepted formats/epochs/capabilities. Do not let stripping a bad header inside
  the reader turn it into the missing case.

Runtime with unknown required capability, unsupported descriptor, or missing
required descriptor:
  Compatibility failure before trusted extraction/verification. Runtime intrinsics
  are not ordinary opaque binary calls; absence cannot be treated as permission to
  assume their semantics. An unrecognized legacy Runtime can only be accepted by
  an explicit tested legacy adapter/identity record; recommend none for 1.0.
  This missing-runtime-descriptor case is distinct from absent library summaries.

3.5 Summary envelope evolution and older dependency producers

Introduce summary format 6 at the handshake boundary. Keep the existing resource
path so old format-5 readers see a present incompatible summary. Retain
analysis-contract-3 only if payload/identity/locator meanings remain unchanged;
format 6 adds mandatory producer/requirements provenance, so it is more than the
prior experiment's compiler-header correction. The new fields are:

  producer: { analysisVersion, extractorId, compilerVersion }
  runtimeContracts: [ { module, runtimeVersion, requires } ]
  requires: [ ...summary interpretation capability identifiers... ]

Retain the current module/source-set/complete/hash/payload checks. Validate all
metadata, including the header; payload hash alone does not bind producer fields.
Use a deterministic envelope digest for cache/evidence identities, with the digest
field excluded from its own hash. Hashes detect changes, not malicious producers.
The supply-chain trust model remains the same as trusting dependency bytecode.

A consumer evaluates the union of (a) current selected Runtime requirements,
(b) producer-recorded runtime semantic requirements, and (c) summary requirements.
Do not reinterpret an old summary using the latest Runtime's requirements alone:
compiled/inlined older code retains its body. Requirements of present transitive
summaries are all validated; absent summaries still yield unknowns. Producer
summaries are local contracts, not copied closures of all dependency payloads.

Compatibility cases, with hypothetical releases:
* L:1.0 was compiled with Analysis 1.0 / Runtime 1.0, both requiring canvas-analysis/1.
  App uses Runtime 1.1 (same requirement), Analysis 1.0, and a certified compiler.
  Accept L's format-6/contract-3 summary without regeneration. Certify the new
  complete Runtime 1.1 / compiler / Analysis 1.0 row with the old actual plugin.
* Runtime 1.2 adds an availability-relevant overload requiring canvas-analysis/2.
  Analysis 1.0 rejects Runtime 1.2 even if L was built with 1.0 and its own summary
  only requires /1. Old producer metadata cannot hide the selected new Runtime.
* L:2.0 compiled with new Analysis against /2 cannot be consumed by Analysis 1.0:
  the summary carries /2, and cannot have been emitted by an old producer that
  failed preflight. Selecting an older Runtime cannot erase that requirement.
* A newer Analysis emitting the same format/epoch/requirements can produce a
  summary readable by older Analysis. Producer release ordering is irrelevant.
  If a new effect is not representable in the old wire contract, the writer must
  declare a new requirement and/or format/epoch; never silently drop the effect.
* A legacy format-5 dependency has no Runtime handshake provenance. For the initial
  1.0 protocol, fail with regeneration guidance. Do not infer trusted provenance
  from the hardcoded prototype-11/2.4.20 header. A later explicit legacy reader is
  possible only with a scoped proof; it is not needed for the first implementation.

Compiler provenance versus summary compatibility:
  The old production reader requires exactly 2.4.20; prior research used a four-
  compiler allowlist as a safe experimental widening. For format 6, recommend
  semantic protocol admission rather than a permanent future-producer compiler
  allowlist. An old consumer need not load the producer's compiler: it reads a
  stable semantic wire contract. Future writers may emit that contract ONLY after
  extraction-equivalence and old-reader binary-consumer certification. Thus the
  old reader accepts a truthful, well-formed format-6 producer it has not seen,
  while the local extractor selection still requires exact compiler certification.
  Kotlin's own binary metadata readability is a separate real compile test.
  This extension is PROPOSED, not established by the four-version experiment.
  First prove the forward-producer/old-reader case with frozen analyzer JARs before
  admitting it; if the proof fails, retain exact producer profiles temporarily and
  report the restriction explicitly rather than claim forward compatibility.

A producer bug can violate a contract without changing a token. The handshake
cannot detect lying artifacts any more than the current payload hash does.
Release conformance tests, artifact identity and a registry incompatibility/
revocation record address discovered defects. Do not promise an offline old
analyzer instantaneous knowledge of later revocations. It need not contact a
registry service during every build; CI can optionally pin a refreshed registry
snapshot for certification checks without modifying semantic acceptance.

3.6 Why this prevents the requested failure modes

New functionality accidentally recognized as an old intrinsic:
  Runtime API/semantic changes undergo capability review, with a negative old-
  analyzer fixture for every analysis-relevant addition. Any unsound old lowering
  requires a new token. Preflight blocks the old extractor before the overloaded
  name can be matched. In addition, harden intrinsic dispatch to recognized
  callable shapes; unsupported overload shapes become Unknown rather than the
  catch-all Canvas-layer path. Neither defense substitutes for the other.

Unknown semantics silently dropped:
  Required token inclusion is checked before decoding/evaluation; unknown wire
  discriminators/required fields are errors. Missing external contracts remain
  Unknown. No fallback parser strips unknown effects or requirement tokens.

Accidental version lockstep:
  No minimum or equality check between Runtime and Analysis. The only strict
  release equality is WITHIN each train and between plugin and its extractors.
  A Runtime version unknown to an old plugin is not itself a rejection reason.

Compatible older plugins rejected:
  The old plugin's understood capabilities suffice even when its embedded registry
  snapshot predates the Runtime. Certification can be added later for that exact
  immutable old plugin, without republishing it. Distinguish semantic acceptance
  from "certification known in this snapshot" in tooling output. Never present an
  unlisted tuple as supported, or require an upgrade solely to refresh a website
  support row. Version ordering never selects the set of compatible Analysis.

Bootstrap limit:
  Arbitrary pre-protocol binaries cannot be retrofitted through metadata alone.
  Embedding a format-6 sentinel summary in Runtime might make old APPLICATION
  verification fail, but it does not fix LIBRARY mode or old standalone extraction.
  Do not use that partial trick as a soundness guarantee. Certify only protocol-
  aware Analysis for 1.0. Preserve old artifacts and give explicit migration advice.

4. ONE AUTHORITATIVE COMPATIBILITY REGISTRY

4.1 Proposed location and schema

compatibility/registry.json is the sole authored compatibility catalog. A small
compatibility/schema.json plus one validator/generator enforce its rules. Avoid a
service, relational database, YAML inheritance language or hand-maintained second
selector table. Bulky immutable test evidence lives outside the JSON and is
referenced by digest. Registry revisions are ordinary reviewed Git commits.

Top-level schema (required unless marked optional):

schemaVersion: 1
kotlinFamilies: map family -> {
  firstStable: exact version, releasedOn: ISO date,
  source: official release URL, releaseId: GitHub numeric ID
}
kotlinReleases: map exact version -> {
  family, releasedOn, releaseId, source, tagCommit,
  artifacts: [coordinate/checksum for compiler and KGP]
}
contracts: map opaque capability -> { specificationPath, specificationSha256 }
releases: {
  runtime: map version -> { commit, tag, artifactManifest, requires },
  analysis: map version -> {
    commit, tag, artifactManifest, capabilities,
    summaryReads: [{format, semantics}], summaryWrites: {format, semantics},
    extractors: [{id, artifact, builtAgainst, compilers:[exact versions]}],
    toolchains: [{compiler, kgp, extractor, environment}]
  }
}
environments: map ID -> {
  gradle: exact version or null for direct compiler consumers,
  java: exact tested major, target: 17, os, bta: boolean or null,
  dependencies: lock/manifest digest
}
evidence: map ID -> {
  kind, sourceCommit, suiteDigest, artifactManifests:[references],
  environment, command, result, runUrl, retainedBundle, sha256,
  completedAt
}
combinations: array of {
  runtime, compiler, kgp: version or null, analysis: version or null,
  environment, verdict: "certified" | "not-certified" | "incompatible",
  evidence:[IDs], certifiedAt: timestamp or null,
  reason: string or null, supersedes: previous record ID or null,
  id: stable unique ID
}

artifactManifest is a content-addressed document containing EVERY actual
publication coordinate, extension/classifier and SHA-256: Runtime JAR/POM/module
metadata/sources/Javadoc/BOM, or plugin marker/implementation and all extractor
publications. It includes the source commit, build toolchain, normalized dependency
lock and relevant semantic fingerprint. Nothing is inferred from a tag alone.
For a proposed release the final manifest reference remains pending and the entry
is not consumer-certified. Do not invent checksums for unavailable artifacts.

There is no manually editable "active" boolean. Support status is a projection:
  incompatible verdict                         -> explicitly incompatible
  no row / not-certified verdict               -> not certified
  certified AND asOf < addMonths(.0 date, 18)   -> certified and actively supported
  certified AND asOf >= that date              -> previously certified, expired

Treat end-of-support as an exclusive ISO date at 00:00 UTC; store this convention
once in schema policy, compute with calendar months (clamp day for month ends),
not 18*30 days. Emit expiresOn in generated views and evidence manifests, and
validate any materialized value. The expiry clock depends on compiler family,
not the Analysis publication date. Mixed compiler/KGP tuples also cannot promise
ongoing KGP support after the KGP family expires: use the earlier family deadline
for that Gradle tuple. The compiler-only runtime row can remain active separately.

The contract does not specify an independent Runtime/Analysis release EOL policy.
Do not add one that silently expires otherwise supported complete combinations.
Preserve old artifacts/rows; expire support for new releases by the Kotlin policy.
A discovered incompatibility may supersede a certified verdict with evidence;
retain its previous certificate for history and show both facts in historical view.
Not-certified is NOT a synonym for failed, and infrastructure failure is not proof
of incompatibility. A failed extractor candidate is evidence about that candidate,
not automatically a verdict that the Kotlin version can never be supported.

kgp=null has exact meaning: compiler-level/runtime-only certification; it is not a
wildcard for any KGP. A Gradle runtime-only row has kgp set and analysis=null.
An Analysis row has both kgp and analysis set. A consumer never has to choose an
Analysis version to query Runtime support. Multiple tested environments can be
represented as separate rows referencing one semantic certificate. UI may group
identical answers, but must preserve distinctions when environment changes results.
Do not advertise all Gradle versions merely because Kotlin lists them as compatible.
Java 17 remains the runtime minimum; newer JVM smoke/regression lanes supplement
that minimum without multiplying every compiler case by every JDK.

4.2 Required validator invariants

* Exact stable versions only in support rows; no 2.3.x, >= or wildcard expansion.
* Every reference resolves. Complete tuple keys are unique in the current view.
* Certified rows require passing evidence for the SAME artifact identities,
  compiler/KGP/selected extractor/environment and a complete-tuple E2E certificate.
* Analyzer's own toolchain tuple must exist; runtime requirements must be a subset
  of analyzer capabilities; summary negotiation must pass. These are necessary,
  not sufficient: the validator does not manufacture complete rows from them.
* Each compiler maps to one extractor within an Analysis release; extractors and
  plugin have one Analysis version. No Runtime dependency in the Analysis BOM
  because no Analysis BOM is needed. Runtime BOM contains only Runtime modules.
* Release manifests cover all artifacts; local checkout/TestKit injection is not
  accepted as external-install evidence. Hash mismatch invalidates evidence reuse.
* No replacement extractor loses any previously supported mapped compiler's full
  certification. No new release silently omits supported combinations.
* A schema/spec/fixture digest change invalidates affected reusable certificates;
  cosmetic website edits do not trigger compiler tests.
* Frozen release records never change artifact bytes/identities. Additional
  certificates or explicit superseding incompatibility records are append-only.
* Illustrative fixtures have an explicit example flag and cannot be admitted into
  a production registry, regardless of their verdict strings.

4.3 Illustrative example

identities and test results there are invented to demonstrate representation.
Official Kotlin dates in the illustration are factual; no combination in that

5. CERTIFICATION EVIDENCE AND MATRIX COST

5.1 Five evidence layers, one complete consumer answer

R — Runtime/compiler consumption:
  Compile public Kotlin source fixtures against the ACTUAL candidate Runtime
  artifacts using every supported exact compiler. Run relevant existing Runtime,
  test and observation/tracing behavioral tests against those artifacts. The code
  under test must not silently be a separately rebuilt Runtime per compiler.
  Include named/default arguments, constructors, generated CanvasKey methods,
  delegation, inline/reified, suspend signatures, overloads/JVM names, and
  conforming third-party interface implementations. Include dependency resolution
  with/without BOM and direct compiler consumption where kgp=null is claimed.

A — Analysis/compiler/KGP:
  For each exact matching tuple, run the existing complete compiler fixtures with
  its selected extractor and the complete TestKit integration suite. Use actual
  matching compiler/stdlib distributions, not a parent-first test classloader that
  accidentally loads root project extraction classes. Track compiler ABI and
  semantic outcomes separately. Retain direct K2 fixtures as test infrastructure.

S — Semantic/metadata conformance:
  Capture normalized contracts and outcome diagnostics for the same fixture source
  under every compiler. Normalize ONLY documented volatile/provenance fields
  (actual compiler/extractor/Analysis version), never effects, unknowns, identities,
  source locations, evaluation ordering, suppressions or JVM locators. Check wire
  roundtrips, future unknown capability rejection, and forward/backward producer
  acceptance using frozen released reader/writer artifacts.

E — Complete tuple installation and execution:
  Resolve real plugin marker/POM and chosen extractor from an isolated Maven repo
  of candidate bytes; use the same bytes later published. No withPluginClasspath,
  includeBuild substitution or mavenLocal fallback. Compile a library and app,
  consume an older-producer library, verify known-safe, missing-key and unknown
  roots in STANDARD/STRICT, package/read summaries, run at JVM 17, and inspect
  selected versions. One invocation can contain multiple outcomes. This is a
  targeted sentinel suite, not another copy of all evaluator tests.

G — Existing-release regression:
  Retain frozen public source and already-compiled clients from 1.0 and later
  additive public APIs, old Analysis JARs, summaries and binary producer fixtures.
  Run them against candidate releases as required below. The 0.x surface is not
  a 1.x ABI baseline; do not preserve the deliberately removed constructors/APIs.

5.2 Exactly what can be reused

Reuse an R certificate across Analysis versions if Runtime bytes, dependency
closure, compiler and runtime environment are identical; Analysis is absent from
that proof. Reuse A across Runtime releases only for fixture-independent compiler
integration behavior whose fixture Runtime/semantic environment is unchanged; new
Runtime semantic behavior still needs its own S/E proof. Reuse evaluator/codec
unit results for identical implementation/test/dependency digests regardless of
compiler variant. A rebuild that changes artifact bytes needs identity verification
and an E test even if semantic fingerprints are identical.

Wire conformance is an explicit factorization, not assumed pairwise compatibility:
(1) each producer output matches the immutable contract corpus and JVM locator
oracle; (2) each reader passes that exact corpus; (3) actual cross-compiler binary
libraries link and produce the same outcomes. Byte-equivalent payloads justify
reusing the decode/evaluate part, not the Kotlin binary metadata/inline/default
handling part. Compiler major/minor/patch labels are not equivalence classes.

Start with all 11x11 producer-compiler/consumer-compiler small binary cases for
one summary contract (121 cases, not 121 complete TestKit suites). This cost is
modest relative to the existing full Gradle suite and avoids inventing Kotlin
metadata equivalence for untested 2.2/2.4 interactions. Thereafter a new compiler
adds a row and column (2K+1 cases); cache each producer JAR by source/compiler/
Runtime/extractor hash. If actual dependencies differ, that is a new producer
identity. Unsupported binary combinations get explicit failures, not normalizing
away compiler diagnostics.

For multiple Analysis releases, partition only by PROVEN equal wire payload and
binary producer identities for the covered corpus. Run each distinct writer and
each frozen reader at least once; run E for every advertised R/C/KGP/A tuple.
When writer meaning, captured inline bodies, locators or runtime requirements
change, invalidate the partition and add direct cross-reader/writer cases. A
coarse semantic epoch is a declared contract, not automatic evidence of equality.

A fresh E test is mandatory for any new complete tuple, changed Runtime bytes,
changed Analysis/plugin/selected extractor bytes, changed KGP/effective compiler,
changed publication shape, changed declared dependency resolution, or changed
certified environment. A selector-only Analysis release can reuse semantic tests
for unchanged extractor bytecode but still needs E for the new packaged artifacts.
Do not reuse a result from prototype-11 as a result for released Analysis 1.0.

5.3 Cost estimate (planning assumptions, not measured CI promises)

Let K=11 exact matching toolchains, R=retained Runtime releases, A=retained Analysis
releases, P=distinct metadata-producing implementations. Matching first means 11
KGP/compiler tuples, not 121. Full mixed support would multiply the expensive
integration lanes and is deliberately deferred.

For the first candidate Runtime/Analysis pair:
* 11 R lanes, reusing existing behavior fixtures rather than rebuilding equivalent
  test logic for each consumer scenario.
* 11 A lanes: 979 existing compiler-test assertions, about 495 real compiler
  invocations; 132 existing TestKit tests, about 671 nested Gradle builds, using
  prior suite counts as a sizing reference, plus new handshake/provenance checks.
* 121 compact cross-compiler binary metadata consumers, 11 cached producers.
* 11 runtime-only compiler rows, 11 matching Gradle runtime-only rows and 11
  complete Analysis rows if all are advertised; direct consumption and external
  runtime installation checks cover their respective rows explicitly.
* A few Java 17/21/current-JVM execution and Gradle boundary checks, not K times
  every JVM times every Gradle release. Broader environment claims need their own
  rows/evidence; begin with one pinned common Gradle distribution.

Illustrative hosted-runner budget: R lane 3–6 minutes, A lane 6–12 minutes,
compact E lane 1–3 minutes, binary cross corpus 10–30 aggregate minutes with warm
caches: approximately 120–300 runner-minutes for initial full certification plus
artifact staging, roughly 25–60 elapsed minutes with six concurrent lanes.
Measure the first real run and revise. Prior local warm runs are far faster and
are not a defensible GitHub cost estimate. Monetary cost is runner-minutes times
the repository's actual billing rate; no pricing assumption is needed here.

For R=4, A=3, K=11: only compatible rows are advertised, at most 132 Analysis E
rows, rather than 132 full behavioral+compiler+TestKit repetitions. Existing R/A
certificates are reused by identity; a new Runtime needs ~11 R lanes and up to
33 small Analysis E lanes; a new Analysis needs 11 A lanes and up to 44 E lanes.
Grouping exact byte-identical certificates prevents repeats but cannot erase the
requirement to certify each complete tuple. The contract gives no general release
EOL escape hatch; growing supported release history is a real ongoing cost.

6.3 Runtime build floor and JVM minimum

Kotlin metadata and inline bodies consumable by the oldest active family. Starting

changing languageVersion/API version on 2.4 or -Xskip-metadata-version-check solves

by POM/GMM on 2.2; test the dependency closure. No bypass of Kotlin metadata
validation is permitted. If source syntax or dependencies require newer Kotlin,
adapt within the contract before claiming 2.2 support; analysis binaries can use
a separate build profile without raising the Runtime consumption floor.

Later 1.x releases may raise this build/consumer floor after expiry, but must retain
JVM linkage of already-compiled supported clients and public behavior. Keep the
public Kotlin module name, JVM names/default bridges, suspend/inline targets and
third-party implementation assumptions stable. Old inlined bodies remain old;
new runtime internals still have to link their supported targets. Java 17 stays
fixed even when compiler support rotates. Run actual candidate artifacts on Java
17 and prevent references to newer JDK APIs; JVM target alone is not that proof.

Explicit Runtime/Analysis conventions assign project.version before publication

Preserve the existing base compiler artifact identity as one real selected profile,
initially the 2.4.20-built profile demonstrated on 2.4.0/2.4.20. Additional artifacts
have explicit profile suffixes, initially 2.3.0 and 2.3.21 if final certification
confirms the research. Do not publish a misleading universal wrapper JAR or an

run on every compiler; each release's manifest/registry lists exact membership.
The seven unresearched versions may require additional profiles. Do not assume
that three binaries suffice for all eleven versions.

All profiles in release A are published at version A, even if their extraction
sources did not change. This is one Analysis release, not independently scheduled

7.2 Practical build arrangement comparison

Option 1 — one build, explicit extractor subprojects, one shared source tree
  RECOMMENDED FIRST. Keep mosaic-compiler-plugin/src/main as the authoritative
  extraction tree. Add small profile projects under analysis-extractors/<profile>
  (or equivalent root project names) whose source sets point to that tree. An
  extractor convention sets compileOnly compiler-embeddable:<builtAgainst>,
  generated profile constants/resources, bundled analysis-core, test inputs and
  publications. One host KGP configures the build; differing compileOnly API JARs
  are ordinary isolated project compilation classpaths. The host compiler used to
  build a plugin is distinct from the compiler ABI it links against.
  Benefit: existing conventions, tasks and publication ownership remain simple.
  Limitation: actual host-produced bytecode/stdlib usage must run in every target
  compiler's classloader, and older/newer compiler APIs must be readable by the
  chosen host. A host producing valid JARs is not target compatibility proof.

Option 2 — included builds per required compilation toolchain
  Use only if a tested profile cannot be built with one host KGP/compiler or the
  Runtime's older metadata floor conflicts with the Analysis build toolchain.
  Independent included builds isolate settings/plugins; they can still point at
  one extraction source tree and one shared convention source. Root release tasks
  coordinate their explicit publication tasks. This is a same-repository build
  boundary, not a new release train. Disable automatic dependency substitution in
  external certification; otherwise the test can accidentally certify source
  projects instead of published binaries.

Option 3 — multiple KGP versions applied to ordinary subprojects
  Reject. The surrounding Gradle plugin classloader can unify already-loaded KGP
  classes; merely changing a version string in a subproject is not reliable
  classloader isolation. Use a single KGP or a real separate build boundary.

Option 4 — custom forked compiler builder for every profile
  Technically possible and similar to research harnesses, but adds hand-written
  incremental/cache/publication logic. No need as the first production build
  arrangement. A separate compiler process may be used in repository TESTS/building
  the tool itself; production analysis must still run inside normal main Kotlin
  compilation and never fork a second Mosaic compiler.

Keep the compiler API out of the Gradle plugin's implementation/runtime classpath,
POM and bundled classes. Keep KGP compileOnly and integrate through its supported
plugin APIs. Never shade compiler classes into an extractor or load extractor
classes in the Gradle daemon just to select one. Selection returns coordinates;
KGP loads the chosen JAR in its compiler environment. analysis-core must have no
IR/KGP dependencies. Match its bytecode/stdlib/serialization usage to every host
in which it is bundled; matching-stdlib tests are necessary, especially for 2.2.
If dependency isolation needs change, make it an evidence-driven focused change,
not an assumed generic shading framework.

8. EXTRACTOR SELECTION, INVALIDATION AND EVOLUTION

8.1 Selection protocol

1. Read installed Analysis identity and its generated finite toolchain/profile
   table; do not use the consuming application's project.version.
2. Obtain actual KGP identity independently from the effective compiler provider.
   Account for BTA being enabled or disabled; compilerVersion can be configured
   but ineffective on older configurations without BTA. A mismatched requested and
   actual compiler is an error, not an excuse to select by KGP.
3. Validate exact (KGP, effective compiler, supported integration environment).
   Start with matching tuples only. Preserve all current project-boundary guards:
   pure JVM main, normal sources, no extra plugins/KSP/options/friends/etc.
4. Select the mapped profile for the effective compiler and Analysis release.
   Resolve via the project's normal dependency repositories, with an exact
   coordinate/version. No latest.release, remote selector lookup, fallback to the
   nearest patch, or automatic installation of a newer Analysis plugin.
5. Validate the resolved profile/version manifest and expected publication
   identity. Resolve duplicate/conflicting artifacts as errors. Inside the actual
   compiler, compare KotlinCompilerVersion.VERSION to the selected exact set.
   Canonicalize only an officially identified stable -release-N suffix; reject
   arbitrary suffixes, RC/EAP/dev builds and unlisted patches.
6. Pass actual compiler, KGP, extractor, Analysis, runtime descriptor digest and
   semantic contract identity into task/shard/summary provenance as appropriate.

Lazy configuration and configuration-cache implementation constraints:
* Use pluginManager.withPlugin, TaskProvider.configure, typed task properties,
  artifact views and Provider mapping. Do not resolve compiler/runtime dependencies
  or finalize compilerVersion in Plugin.apply. Do not fetch the registry online.
* Kotlin's compilerVersion API warns that reading it finalizes it. The current
  getPluginArtifact API returns a concrete SubpluginArtifact, not a Provider.
  Materialize selection at that KGP callback only after consumer configuration;
  test that a compilerVersion set late in the user's kotlin block still wins.
  Prior automatic-selector research is evidence for ordinary configuration on four
  versions, not proof of all lifecycle orderings or 2.2. See Kotlin issue KT-79853
  for the provider limitation. Do not claim fully lazy selection merely because
  a Provider.get() is hidden in a helper.
* If a target KGP invokes that callback too early, use a narrowly scoped lazy
  dependency substitution/coordinate-resolution hook on the compiler-plugin
  configuration, generated from the same table, or isolate that integration until
  proven. No broad afterEvaluate mutation or task-action classpath replacement.
  This timing probe is an acceptance gate before certifying such a KGP.
* Task actions retain primitive/value inputs and FileCollections, not Project,
  Configuration or ResolvedArtifactResult objects. Copy origin identities into
  serializable input records. Run two builds with configuration cache, relocated
  cache restore, project dependencies and parallel tasks as existing tests do.

The official BTA documentation allows different KGP/compiler versions but warns
that compiler plugins can fail. Previous research showed Kotlin scripting plugins
needed alignment in both upgrade and downgrade directions. Mixed tuples remain
explicitly not certified initially. A later focused PR may align only recognized
Kotlin-default artifacts with the effective compiler; it must not relax the ban on
arbitrary other compiler plugins or add a universal resolutionStrategy force.
Certify each mixed tuple separately, including actual BTA/default-plugin versions.

8.2 Incremental and build-cache identities

Bump internal shardVersion from 2 to 3 (or next unused internal version) and add
Analysis/extractor/actual compiler/runtime-contract provenance. The compilation
output directory includes a deterministic extraction identity, or is cleared
through a correctly modeled version-change compilation step; never assemble old
shards into a new identity. A full re-extraction is required when that identity
changes, including sources Kotlin might otherwise consider unchanged. Prefer an
identity-specific output namespace plus declared compile inputs with a test proving
all current shards are regenerated; reject incomplete results rather than reuse.

The assembler verifies every current shard has the expected identity; source
inventory still decides membership. Emit explicit empty complete format-6 metadata
when Kotlin reports NO_SOURCE using the validated configuration identity. Check
both version switches and switching back, cache relocation, failed-build recovery,
last-source deletion, and stale files left by a previous failed compiler.

Keep dependency summary content separate from source compilation. A dependency
body-only semantic change reruns validation/evaluation/packaging as necessary,
without forcing unchanged consumer compilation. Runtime descriptor content changes
are compilation identity changes; ordinary dependency summary changes are not.
Use content-sensitive resource inputs, not only ABI-normalized @CompileClasspath,
since a descriptor/resource change can leave class signatures unchanged. Include
selected identities, strictness/roots, local/dependency summaries and handshake
inputs in task fingerprints; a successful cache hit must have validated the same
requirements. Regenerating a certificate/website date must not invalidate compiler
outputs.

8.3 Adapter evolution algorithm (strict replacement rule)

For a newly released stable compiler:
1. Run each plausible existing extractor candidate on linkage smoke, then run the
   complete requirements on any passing candidate. Guards may be widened only in
   an isolated candidate build; widening a guard is never evidence of compatibility.
2. If existing binaries fail, recompile UNCHANGED shared sources against the new
   compiler API. Run the full extraction/semantic/KGP/metadata/installation suite.
3. If sources no longer compile or semantics differ, attempt a small clean shared
   change or one tiny profile-specific compatibility file at the demonstrated API
   seam (for example registrar ABI or origin accessor). Re-run every affected
   profile. Keep extraction logic single-owned; do not fork SourceContractExtractor.
4. If necessary retain a distinct profile binary. No broad Kotlin-version if/when
   checks throughout extraction, reflection dispatch platform, or generic adapter
   framework without demonstrated variability requiring it.

An updated binary may replace/consolidate an existing profile ONLY if EVERY
previously supported compiler mapped to that profile passes its COMPLETE
certification requirements on the replacement, including expired historical
members if the action is called replacement of that profile. Same compiler family
or unchanged source is insufficient. The proven 2.3.0/2.3.21 getter break is the
counterexample. Save the before/after mapping and referenced certificates; make
this a registry validator/release gate, not a reviewer convention alone.

Retirement is different from replacement. Once an entire mapped family's support
expires, a NEW Analysis release may omit that old profile. Preserve all older
published binaries and their mappings/registry history. If retiring expired
members from a combined profile, record a new profile/mapping as retirement plus
new certification rather than claiming the replacement passed the old membership.
Consolidation can reduce future build count only with the universal revalidation
above. Never delete or overwrite an old artifact, and never make users select
profile artifacts manually.

9. MINIMAL RELEASE DISCOVERY AND REMEDIATION AUTOMATION

PROPOSED infrastructure: one new kotlin-certification.yml workflow (schedule,
workflow_dispatch and reusable workflow_call), one small deterministic discovery/
registry-validation script, and train parameters added to the existing release
workflow. Keep actual test plans in versioned repository tasks/scripts, not a
large collection of nearly identical workflow files.

Daily run, e.g. 07:23 UTC (avoid the top of the hour):
1. Read the official paginated stable-release inventory and registry; retain the
   API response identity and source date. Also notice RC/EAP entries for a weekly
   cheap warning lane, never a stable support row. Scheduled workflows run from
   the default branch; explicitly checkout the intended reviewed develop SHA for
   candidate tests. Record both workflow SHA and tested SHA. Do not assume schedule
   on a non-default branch runs automatically.
2. Compute work keys from Kotlin version + candidate source SHA + artifact/test
   plan hashes. Detect all unprocessed stable patches in active families, including
   backfill patches on older active families. Do not only inspect /releases/latest.
3. Reuse successful exact-identity certificates; skip identical open PR/work keys.
   Run a small linkage smoke before costly suites. Distinguish upstream artifact
   propagation/network failure from reproducible compatibility failure; bounded
   retry/backoff for the former, investigation for the latter.
4. Run R and A/S/E candidate plans with pinned inputs. If an existing released
   plugin rejects the version via its exact selector, it is not suddenly compatible
   because a modified candidate passes. Prepare a new Analysis release containing
   the selection/guard update, even when the binary implementation is otherwise
   unchanged. Runtime-only certification can often be added to existing Runtime
   artifacts without releasing Runtime again.
5. Persist evidence: source/test/workflow SHAs, dependency/artifact hashes,
   toolchains, commands, JUnit, normalized and original summaries, expected unknown
   diagnostics, classpaths and a minimal reproduction. Hash the evidence bundle.
   Upload run artifacts for quick inspection; retain authoritative successful and
   incompatibility evidence in durable release assets/content-addressed storage
   associated with the reviewed certificate. Do not rely on an expiring Actions
   artifact URL as the only provenance for permanent historical support.
6. On success, prepare one focused registry/release-candidate PR. Only rows proved
   against existing released bytes become proposed certified rows immediately;
   new-release rows remain pending/not-certified until approved publication and
   installed-byte checks. Human merge and publication approval remain mandatory.
7. On reproducible failure, create/update one version-keyed investigation issue/PR
   and invoke the approved agent runner with the reproduction and an allowlisted
   source/test scope. Its task is diagnose ABI/semantic/build integration failure,
   attempt the ordered adapter evolution, and propose a focused remediation PR
   with regression evidence. It cannot merge or publish. No agent delegation or
   remediation run was performed in THIS investigation.

Idempotence/concurrency:
  One discovery concurrency group, cancel-in-progress=false; candidate jobs keyed
  by compiler plus source/test identity. Use one branch such as
  automation/kotlin-2.4.21 and update it using expected-head checks; do not overwrite
  a human's edits. Re-read the registry/base before opening/updating a PR. Different
  candidates may test concurrently, but final registry merges revalidate against
  current state. Manual retry reuses the work key unless inputs actually changed.

Costs and notifications:
  No new release => one small API/validation job, no Gradle matrix. Cap simultaneous
  costly lanes, reuse dependency downloads and producer artifacts by verified
  digest, set timeouts and a retry limit. Failed compatibility, missing evidence,
  stalled publication and missed schedules appear in the job summary and a single
  existing version-keyed issue. GitHub maintainers own notifications; no external
  Slack/email integration is required. Use manual dispatch as schedule recovery.

Security/permissions:
  Discovery and tests get contents:read only and no publication/signing secrets.
  A separate trusted PR-writer job gets narrowly scoped contents/pull-requests
  writes and consumes validated structured results, never executes uploaded code.
  Pin Actions to commit SHAs, restrict fetched coordinates/repos, verify wrappers/
  dependencies, use disposable runners with resource limits. Release notes, logs
  and dependency source text are untrusted data for agents. Do not run fork PR code
  under pull_request_target with secrets. The agent gets no release credentials,
  workflow/protection edits or authority to edit registry verdicts without evidence.
  Current GitHub documentation says GITHUB_TOKEN-created/updated PRs can trigger
  approval-required workflow runs, while ordinary token-generated pushes do not
  trigger new runs. Explicit workflow_dispatch is another supported route. Use
  approved PR runs or explicit dispatch and verify required checks ran on the final
  PR SHA; a bot-created PR alone is not evidence that validation executed.

Soundness protection:
  Fixes may not remove unknowns, weaken STRICT, suppress diagnostics, broaden
  compiler guards without tests, delete failing fixtures, or stamp an old semantic
  contract onto new meanings. Deterministic schema/negative-corpus gates and human
  semantic review are required. A contract change must declare its new capability
  or epoch and retain tests of old-reader rejection. If automation cannot find a
  sound fix, leave the version not certified, attach evidence and request review;
  it must not edit the authoritative compatibility guarantees to declare success.

12. VALIDATION AND RELEASE GATES

12.1 Smallest reliable ownership

analysis-core owns pure descriptor negotiation, metadata grammar/epochs/capabilities,
required-field/unknown-token behavior, evaluator unknown outcomes and format corpus.
compiler-plugin owns symbol-shape recognition, IR-to-contract fidelity, compiler
version assertion and shard provenance. Gradle plugin tests own resolved identities,
selection, task ordering, application/library/graph/package gates, cache behavior,
publication and external installation. Runtime modules retain their existing
behavior tests; a dedicated compatibility fixture project compiles frozen public
clients and checks ABI/source behavior against actual artifacts. Build/release
logic owns coordinated versions, manifests and registry validity. Avoid testing
private helper names or making multiple suites assert the same parser behavior.

Public compatibility gate:
  Freeze 1.0 public Kotlin and JVM API signatures plus source/compiled fixtures.
  Compare every later release to the baseline AND the accumulated additive 1.x
  surface, not just the immediately previous patch. A signature diff tool alone
  cannot prove named arguments, overload resolution, generated methods, default
  arguments, third-party implementations or documented behavior. Compile source
  fixtures on certified compilers; run frozen already-compiled binaries against
  new JARs on Java 17 with compatible dependencies. Preserve observation SPI and
  both tracing installation overloads, not just mosaic-core Canvas operations.
  Reuse existing lifecycle/cancellation/cache/Canvas/resource/observation/tracing
  tests for observable behavior; add only missing contract witnesses.

Required new regression witnesses:
* An actual frozen older analyzer accepts a synthetic newer Runtime descriptor
  with the same requirement, and rejects an unknown token, unknown descriptor
  version, duplicate fields and absent descriptor. Test both same compiler and
  already-certified cross-version dependency producers.
* Old reader/new writer and new reader/old writer preserve VERIFIED/MISSING/
  UNVERIFIED outcomes, strict enforcement, payload identities and locators.
* A new same-name runtime overload cannot fall through an old intrinsic path and
  claim known effects. Capability omission makes the release conformance test fail.
* Missing ordinary summary remains Unknown; present incompatible summary fails
  for application, library, graph and packaging. A no-root/NO_SOURCE build does
  not bypass the compatibility gate. Failure never leaves a usable success report.
* Resolved runtimeVersion differs from requested version; transitive upgrade,
  compile/runtime divergence, forced module mixture, project dependency JAR,
  local JAR, duplicate resource and shadowed runtime owner all behave explicitly.
* Runtime requirement-only resource change invalidates extraction; ordinary
  dependency-summary-only change preserves compile incrementality and reruns
  verification. Check clean/incremental/cache-restored equality in both cases.
* Compiler/extractor/Analysis switch and switch-back cannot assemble old shards;
  relocation/configuration-cache/recovery/last-source removal preserve truth.
* External plugins DSL and runtime-only install select exactly staged manifests,
  without injected plugin classes, includeBuild or mavenLocal. Check marker/POM/
  GMM, BOM constraints, sources/Javadoc, manifests and compiler/KGP leakage.

12.2 Check cadence

Every commit/PR:
  Existing root and examples required checks at baseline toolchain; registry/schema
  and generated-data consistency; descriptor/codec/unknown negative unit corpus;
  changed extraction profiles' direct compiler suites; baseline TestKit; public
  API comparison on Runtime changes. Trigger relevant certification lanes when
  source/build/semantic inputs change. Documentation-only registry display edits
  need projection validation, not all Kotlin tests. Baseline check is not evidence
  to promote untouched versions automatically.

  Full R/A at the exact new matching compiler/KGP, complete E, S corpus plus new
  producer/consumer row/column, configuration/build cache/version-switch, publication
  shape checks. If replacing a mapped binary, every previously mapped compiler's
  complete requirements rerun. RC lanes provide early warning only.

Runtime release:
  All active exact compiler R lanes against the new actual bytes; complete public
  source/ABI/behavior gates; descriptor audit; small E for every still-compatible
  supported Analysis/compiler tuple including actual OLD plugin JARs; updated S
  whenever analysis-relevant semantics change. No automatic Analysis upgrade to
  make testing easier. Stage and install all four Runtime modules and BOM.

Analysis release:
  Full A/S for all active mapped compiler/KGP tuples; retain supported combinations
  with Runtime releases; small E against the retained compatible Runtime set;
  cross-version producer/reader checks and all profile/selection/provenance gates;
  external coordinated-variant install. An incompatible metadata change requires
  explicit migration/regeneration diagnostics and historic reader tests.

Periodic extended regression (weekly or monthly depending on observed cost):

14. REMAINING RISKS AND DECISIONS BEFORE IMPLEMENTATION

Required decisions to begin PR 1 (recommendations in this report are concrete):
* Approve the fixed descriptor path/v1 fail-closed grammar and initial coarse
  capability meaning. This is a durable inter-tool commitment even though Analysis
  DSL/wire/report surfaces are otherwise provisional.
* Approve the protocol-aware Analysis baseline; pre-protocol 0.x cannot be promised
  retrospective fail-closed negotiation. Approve format-5 regeneration at migration.
* Confirm the Runtime requirement review owner and freeze the analysis scope of
  canvas-analysis/1 against the existing public API matrix. No promise of complete
  application correctness is added.

Technical probes needed before broader support/publication, not reasons to delay
implementing the current-toolchain handshake:
* Kotlin 2.2 consumption of actual Runtime/dependency metadata and Java 17 execution.
* KGP callback timing/classloader compatibility on 2.2 and the previously untested
  patches; profile count cannot be known from version names alone.
* Full format-6 future-producer/old-reader conformance. The proposed stable semantic
  protocol intentionally goes beyond the research's exact producer allowlist.
* Intrinsic overload-shape coverage and capability governance: no automatic scanner
  can prove a hand-authored runtime requirement is truthful. Require API/behavior
  review and negative old-analyzer witnesses for relevant additions.
* Gradle distribution scope: start with an actually tested common 8.14.x wrapper
  distribution (current wrapper is 8.14.4) and verify its pairing with 2.2; official
  KGP ranges are external context, not Mosaic evidence. Broaden only with testing.
* Runtime/Analysis release numbering first values are maintainer choices; do not
  infer them from the current 0.7.0 placeholder. Examples use 1.0.0 only illustratively.
* Durable evidence hosting/retention and approved agent runner/credential need an
  operational owner before PR 8. No new service is necessary if release assets
  meet retention/integrity needs; Actions retention alone is insufficient.
* Offline revocation has a real limit. Unknown mandatory semantics are fail-closed;
  a bug in an already-trusted producer is repaired through new artifacts/advisories,
  not a fictional ability to update old offline analyzers remotely.
* Actual Mosaic 1.0 release date is required to close the backlog. October 7 is this
  investigation's explicit baseline; it does not restart any Kotlin support clock.

No separate repository, generic adapter framework, public analyzer SPI, per-method
capability matrix, network-dependent plugin selector or independently versioned
extractor train is justified by present evidence.
